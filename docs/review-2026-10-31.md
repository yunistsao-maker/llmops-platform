# Design review, 2026-10-31

Review of "LLMOps 平台完整專案設計" (v1) before building, against two new constraints: every component deploys
on its own, and everything except the models runs on-prem (AWS first, as a test).

## What v1 had to change

| v1 | Problem | v2 |
|---|---|---|
| Built on GCP services: GKE, Cloud Run, Workflows, Pub/Sub, IAP, Cloud SQL, BigQuery, Secure Web Proxy | none of it exists on-prem | Kubernetes, PostgreSQL, S3-compatible storage, OIDC, company proxy; no cloud-specific API in the code |
| Three big blocks (crawl, test, back office) | cannot deploy separately; permissions mixed | 15 components, one Dockerfile and least privilege each |
| Components talk over Pub/Sub | needs a message system on-prem | events and work queue in PostgreSQL; swap for Kafka / NATS later if volume demands |
| Identity built on GCP service accounts | none on-prem | internal PKI issues X.509 certificates, mapped to each cloud's certificate-based identity |
| On-prem runner pulls work to get through the firewall | no longer needed once services are on-prem | runner and gateway in the same cluster; direct cloud tests go out through the proxy |
| Research agent on AgentCore, Lambda, Step Functions, Amplify | cannot run on-prem | agent as a container CLI; pluggable search with an official-page list when no search service exists; publishing split out as `publisher` |
| Test results in BigQuery | none on-prem | PostgreSQL for results, object storage for case-level records |
| Highlights, countdown and plain-language copy hard-coded in the prototype's build script | nobody can edit them in production | editorial data, merged by view-builder |
| Chat and form helper use the claude.ai runtime | not available in production | assistant-api through the gateway |
| AWS test on RDS, S3, IRSA | would test something different from on-prem | PostgreSQL and an S3-compatible store inside k3s, as on-prem |
| Image and package sources | supply-chain risk (the LiteLLM 1.107.0 incident, 10-21) | base images and LiteLLM pinned by digest; Python packages locked with hashes |
| Sandbox on GKE Sandbox | the on-prem cluster may not offer gVisor | use gVisor or Kata if offered; otherwise a separate VM for SEC-15, 22, 27 |

## Found while building

| Finding | Decision |
|---|---|
| MinIO images could not be pulled from the build network | versitygw (Apache-2.0, S3-compatible, posix backend) for local and test; on-prem uses the company's S3-compatible storage |
| The build network inspects TLS; `pip` inside `docker build` failed | optional BuildKit secret `build_ca` (never stored in an image); `tools/docker-build.sh` |
| LiteLLM v1.105.2 reports its version only on the authenticated `/health/readiness/details` | `GatewayClient.gateway_version()` tries that first |
| LiteLLM downloads its price map from GitHub at start | `LITELLM_LOCAL_MODEL_COST_MAP=True`; the map inside the pinned image is used |
| The LiteLLM non-root image runs as UID 65534, not 10001 | allowed exception, set explicitly in the manifests |
| A VPC CIDR inside 10.42.0.0/16 overlaps k3s's pod network | test VPC 10.20.0.0/24 |
| Pods could use the instance role through IMDS | IMDS hop limit 1 when Roles Anywhere is on; only certificate holders reach Bedrock |
| `curl get.k3s.io \| sh` runs an unpinned script | install script taken from the pinned k3s release tag (it verifies the binary's SHA-256) |
| Per-component manifests, compose services and the handoff table drift apart when written by hand | one description (`deploy/components.yaml`) renders all three; CI checks they are current |
| Gateway master key in every component | one virtual key per component, limited to its model aliases and budgeted; only key-provisioner holds an admin key |

## Open decisions

- Which S3-compatible storage on-prem; which IdP; who issues and rotates the gateway and test-runner certificates.
- Our gateway or the company's existing one on-prem (both work; see `envs/onprem-staging` in llmops-deploy).
- Event queue in PostgreSQL, or the company's Kafka / RabbitMQ if one exists.
- Search service for the research agent on-prem (until then: the official-page list).
- Secrets in Vault or Kubernetes Secrets.
- The request form's G2 / G8 rules are still provisional; pass thresholds follow the security matrix, 10% where it gives none.
